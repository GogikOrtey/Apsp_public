# APSP_public — как устроен проект

Этот `README.md` — **описание внутренней связности** проекта: какие модули за что отвечают и как идёт поток данных от фронта до генерации результата.

## Быстрый ориентир: как «пощупать» проект

Для запуска проекта нужно запустить MAIN_APP.py
И зайти на http://127.0.0.1:5000

Технически это означает запуск Flask-фронта через `MAIN_APP.py` и переход на `http://127.0.0.1:5000`.

## Фронт (Flask + Jinja)

Фронт написан на **Flask** и шаблонах **Jinja2** (см. `Apsp_front/`).

### UI: 3 основные страницы

Роуты определены в `Apsp_front/app.py`:

- **Страница 1** — ввод URL сайта:
  - `/main_page_1`
  - пользователь задаёт ссылку на сайт (исходный URL генерации)
- **Страница 2** — “наблюдение за генерацией”:
  - `/main_page_2/<uid>/`
  - UI показывает прогресс по шагам (в текущем UX это **10 шагов**; процесс долгий, порядка **~15 минут**)
- **Страница 3** — результат:
  - `/main_page_3/<uid>/`
  - UI отдаёт сгенерированный результат (код/файлы/логи) для конкретного задания

Шаблоны лежат в `Apsp_front/templates/` (например, `main_page_1.html`, `main_page_2.html`, `main_page_3.html`).

## Параллельные задания и UID

В сервисе реализован функционал **параллельных запусков** генерации: можно стартовать несколько задач одновременно, и каждая получает **уникальный UID**.

Это сделано через реестр задач `TaskRegistry`:

- **Создание задачи**: генерируется UID и создаётся директория задачи
  - UID формируется как первые 12 символов `uuid4().hex`
  - см. `task_runtime/task_registry.py`
- **Запуск**: задача уходит в пул воркеров (внутри — Playwright pool)
  - лимит параллелизма задаётся `max_workers` (в текущей конфигурации — до 10)

Фронт хранит состояние задач и “привязывает” UI к конкретному `uid` (поэтому URL страниц 2/3 содержат `uid`).

## Главная точка входа генерации

Основная функция старта процесса генерации:
`@new_program/main_processer.py:152`

Ключевая идея: `main_processer(input_url, uid, task_dir, page)` получает URL, подготавливает/нормализует его, обеспечивает наличие Playwright-страницы (`page`) и дальше запускает основную цепочку генерации.

## Что внутри `new_program/` (LLM/Agent handlers)

`main_processer()` опирается на набор модулей из папки `new_program/`: там лежат “обработчики” и данные, которые используются для:

- **вызовов LLM** (запросы/промпты/форматы)
- **вызовов агента**
- **хранения/записи промежуточных и финальных артефактов**
  - задачи, результаты, вспомогательные файлы и т.п.

Идея папки: держать рядом всё, что нужно “пайплайну генерации”, чтобы он был расширяемым.

## Reasoning-агент (reasoning_agent/)

В проекте есть “блестящий” функционал для вызова агента: `agent_main.py` и всё в папке `reasoning_agent/`.

Концепция агента:

- агенту нужна **задача** (текст/цель)
- нужен **набор полей результата** (schema) и **шаблон результата** (template), которые он будет заполнять
- нужен **план шагов** (steps), по которому агент движется; если план не задан — он генерируется
- дальше агент сам выбирает инструменты и выполняет шаги, обновляя result

Фактически это “оркестратор” над LLM + инструментами: модель выбирает действие/инструмент, выполняет его, пишет данные в result, и завершает работу статусом `DONE|FAILED`.

## Интеграция агента с Playwright (playwright_tool/)

В проекте реализовано взаимодействие агента с Playwright: скрипты лежат в `playwright_tool/`.

Ключевой файл — `playwright_tool/playwright_toolkit.py`: там описано много инструментов, которыми агент может **в реальном времени** взаимодействовать с содержимым браузера (переходы, клики, ожидания, поиск элементов, чтение HTML и т.д.).

Это даёт агенту “руки” для исследования сайта прямо во время генерации.
